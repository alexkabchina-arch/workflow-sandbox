# /ship

Конец работы над веткой. Сессия тикета мёржа **не ждёт**: включает авто-мёрж и завершается,
GitHub сливает PR сам после зелёного CI и отметки ревью. Проектные команды — из профиля проекта
`docs/agents/profile.md` (тесты, линтеры, ожидаемые job CI, критичные зоны, рецепт `/verify`).

Шаги строго по порядку. Красный шаг — стоп: исправить и пройти шаг заново или, если исправить
нельзя, — отчёт об остановке (ниже).

Тот же сбой второй раз без новой гипотезы — стоп и отчёт об остановке. Повтор без новой гипотезы
только тратит предел объёма сессии.

## Отчёт об остановке

PR создаётся только у выполненного тикета. Довести нельзя (критерий не подтверждён, тот же сбой
второй раз, ревью или `/verify` не состоялись) — отчёт владельцу комментарием, без push и без PR:

```bash
scripts/canon/ship-finish --unconfirmed "Отчёт об остановке: …"
```

- PR ветки нет — комментарий в тикете (номер — из ветки `ticket-N` или `ticket-N-…`) и метка
  `ready-for-human` на тикете; push и PR не делаются, ветка остаётся в worktree (незакоммиченные
  правки не мешают).
- PR уже есть (возврат, повторный `/ship`) — комментарий и метка на PR, PR переводится в черновик,
  авто-мёрж выключается; новые коммиты не пушатся.
- Отчёт пишется при каждом вызове: Stop-хук засчитывает только отчёт этой сессии. Вызывать один
  раз на остановку.

Содержание — понятно владельцу без сессии: что сделано; **локальный итог тестов и линтеров**
(команды и коды выхода шага 3: CI в проекте идёт только по PR, без PR его нет); что не прошло и
что пробовал; ссылка на тикет техдолга шага 2, если заведён; вопрос; варианты; рекомендация.
Первая строка — «Отчёт об остановке» (её ищет Stop-хук). Не проходит и `ship-finish` (ветка не `ticket-N` и не `ticket-N-…`, сбой `gh`) — то же
вручную: есть PR — `gh pr merge <PR> --disable-auto`, `gh pr ready <PR> --undo`, `gh pr edit <PR>
--add-label ready-for-human`, `gh pr comment <PR> --body-file <отчёт.md>`; PR нет — `gh issue
comment <N> --body-file <отчёт.md>` и `gh issue edit <N> --add-label ready-for-human`.

## 1. Ревью ошибок

Вся работа закоммичена. Из корня проекта, обычным Bash (не в фоне) с таймаутом 45 минут
(`timeout: 2700000`):

```bash
scripts/canon/review /tmp/review-<ветка>.json
```

- Код 0 и строка `review: пропущено` — дифф только из документов (`.claude/**` — скиллы, агенты,
  правила, а также `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` и профиль `docs/agents/profile.md` — не документы,
  ревьюятся). Отчёт о пропуске всё равно пишется в `/tmp/review-<ветка>.json`.
- Код 0 — находки списком в `/tmp/review-<ветка>.md`, их число — в строке `review: … находок: N`;
  «Находок нет» — законный итог. Строку `review: предупреждение: …` перенести в тело PR
  дословно; строку `review: ready-for-human: …` — передать на шаге 7 (`--ready-for-human`).
- Код 1 или 2 — ревью не состоялось (и когда список находок не распознан): стоп, причина из
  stderr — в отчёт пользователю. Без состоявшегося ревью отметку не ставить.

Отчёт `/tmp/review-<ветка>.json` — пропуск к отметке: `ship-finish` ставит её только по нему
(шаг 7). Отчёт хранит, какой диапазон проверен (`canon_review.base_sha`, `canon_review.head`).

**Полное ревью — одно на ветку, повторного нет** (решение канона
`docs/decisions/2026-10-03-no-re-review.md`). Коммиты после него — исправления по находкам, правки по тестам,
исправления возврата по красному CI — проверяют тесты, CI и `/verify`, не ревью. `ship-finish`
назовёт их в описании отметки и допишет списком в тело PR.

Повторный `/ship` (после обрыва, возврат) берёт уже готовый отчёт ветки — ревью заново не
запускается. Отчёта нет (`/tmp` очищен) или он по коду уже слитого PR ветки (`ship-finish`
откажет: новых коммитов он не видел) — ревью ветки заново, один раз. Скрипт, запущенный снова с
тем же путём отчёта, переносит старый в `/tmp/review-<ветка>.prev.md` (и `.prev.json`): упади
новый прогон — оплаченные находки там.

## 2. Исправления

Ревью только находит, исправляет сессия. Каждую находку сверить с кодом и решить:

- **исправлено** — дефект, который вносит ветка: в изменённых строках или вне их, если ветка
  делает его достижимым (новый вызов, новые входные данные); сессия признала находку верной —
  чинить в этой ветке, отдельным коммитом. Место строки находки не решает, решает причина;
- **отклонено** — находка неверна: одна строка, почему;
- **техдолг** — дефект в коде вне диффа, который был и до ветки: тег `(correctness)`,
  `(security)` или `(без категории)` (в скобках после пути в `/tmp/review-<ветка>.md`; категория у
  ревью необязательна, и молча такая находка не пропадает), со сценарием отказа или без. В этой
  ветке **не чинить**, записать тикетом (ниже);
- **не записано** — прочие находки вне диффа с тегом иной категории (упрощение, эффективность,
  соглашения), даже со строкой «Сценарий:»: никуда не записываются, в тело PR идёт только их число.

Тикет техдолга — все находки «техдолг» ветки в одном месте, `<N>` — тикет ветки:

1. Прошлый `/ship` ветки их уже записал (`gh issue list --state all --search "\"Техдолг после
   #<N>\" in:title,comments"`) — дописать туда только те, которых там ещё нет; новых нет — ничего.
2. Иначе есть открытый тикет техдолга, к которому относятся **все** находки ветки (те же файлы
   или модуль; `gh issue list --state open --search "техдолг in:title"`) — дописать комментарием
   (`gh issue comment <тикет> --body-file …`) с первой строкой «Техдолг после #<N>».
3. Иначе — новый тикет; метка — название роли `needs-triage` из `docs/agents/triage-labels.md`
   проекта:

   ```bash
   gh issue create --title "Техдолг после #<N>: <область>" --label needs-triage \
       --body-file /tmp/techdebt-<ветка>.md
   ```

В теле — по каждой находке: файл и строка, суть, сценарий отказа из ревью (если он есть). Находок «техдолг» нет —
тикета нет. `gh` отказал — стоп: отчёт об остановке, находки «техдолг» — в нём. Ссылка на тикет —
в тело PR (шаг 5) и в отчёт об остановке, если `/ship` остановится позже.

## 3. Тесты и линтеры

Полный сюит и все линтеры командами из раздела «Команды» профиля. Красное — исправить и
прогнать заново.

**Красный тест вне диффа** — падение не из-за ветки: тот же тест красный и на `origin/main`, или
сбой явно об окружении (соединение, порт, контейнер, база). Падает тест неизменённого кода, который
вызывает изменённый, — это регрессия ветки: чинить, как любое красное. Вне диффа — в ветке не
чинить: проверить окружение **своей** сессии (как его готовят раздел «Окружение» профиля и команда
тестов; адреса сессии, если проект их ведёт, — например `.session-meta` в корне worktree), общее
окружение и чужие сессии не трогать; поправить найденное и перезапустить ту же команду **один
раз**. Причину и что поправлено — в Evidence (шаг 5) и в итог. Красный второй раз — стоп по общему
правилу: отчёт об остановке.

Линтер или формат красный только на файлах вне диффа (например, обновился инструмент) — в ветке
не чинить: стоп, отчёт об остановке.

Долгие команды — через `run-log`, не через пайп: у `команда | tail` код выхода от `tail`, и
красный прогон читается как зелёный. Каждая команда профиля — отдельным вызовом из корня проекта,
обычным Bash (не в фоне) с таймаутом 45 минут (`timeout: 2700000`). Команда в профиле уже начинается
с `scripts/canon/run-log` — запускать как есть, второй раз не оборачивать; ещё не обёрнута —
обернуть:

```bash
scripts/canon/run-log -l tests -- <команда тестов из профиля>
```

Итог — код выхода вызова и последняя строка `run-log: завершено с кодом N`; на экране хвост,
полный вывод — в логе из той же строки. Ненулевой код — шаг красный, даже если хвост выглядит
зелёным. Длинный лог читать через `docs-scout`, не целиком в свой контекст.

## 4. `/verify`

По смыслу, а не по путям. Обязательна, когда ветка меняет наблюдаемое поведение (интерфейс,
ответ API, записываемые данные). Иначе — пропуск одной строкой в Evidence с причиной
(«`/verify` не нужен: …»), например «правка только документации».

Проверяет встроенный `/verify` — скриптом канона: он запускает дочерний `claude -p` с явным
диапазоном диффа, на закреплённой модели (проверяющий не слабее исполнителя), без меток сессии
тикета и сам проверяет, что проверка состоялась. `<ветка>` в путях ниже — имя ветки с `/`,
заменённым на `-`.

Критерии тикета — в файл `/tmp/verify-criteria-<ветка>.txt` (номер тикета и критерии приёмки,
как есть). Из корня проекта, обычным Bash (не в фоне) с таймаутом 45 минут (`timeout: 2700000`):

```bash
scripts/canon/verify /tmp/verify-<ветка>.json --criteria-file /tmp/verify-criteria-<ветка>.txt
```

- Код 0 и строка `verify: … PASS` или `… FAIL` — проверка состоялась: итог — поле схемы
  `verdict`, не текст; что проверено — в `/tmp/verify-<ветка>.md`, стоимость — в той же строке.
  В Evidence: что проверено (шаги, пробы мимо счастливого пути) и итог PASS / FAIL. Строку
  `verify: предупреждение: …` перенести в тело PR дословно; строку `verify: ready-for-human: …` —
  передать на шаге 7 (`--ready-for-human`), как у ревью; есть обе строки — одним аргументом через
  «; ».
- Код 0 и строка `verify: пропущено` — в диффе нет изменений (ветка без своих коммитов).
- Строка `verify: /verify оставил в рабочем дереве: …` (при коде 1 — в stderr) — разобрать каждый
  пункт: рецепт `.claude/skills/run-*` — стоп, см. ниже, `.claude/skills/verify/` — удалить, тестовые
  файлы — откатить; «коммиты /verify поверх ветки» — разобрать их файлы так же, лишнее откатить
  отдельным коммитом; «ветка сменилась» или «история ветки переписана» — стоп, ничего не
  откатывать, пункт — в отчёт.
- Код 1 или 2 — проверка не состоялась: стоп, причина и стоимость из stderr — в отчёт. `BLOCKED`
  (проверить не удалось: нет рецепта, нужен ответ человека) и «итог не распознан» — ответ
  `/verify` в `/tmp/verify-<ветка>.raw.md`, его суть — в отчёт. Отчёт прошлого состоявшегося
  прогона, если был, — в `/tmp/verify-<ветка>.prev.md`.
- Код 2 из-за своего `verify` (скилл `skills/verify/` или с `name: verify`, команда
  `commands/**/verify.md`): незакоммиченный в проекте — удалить и запустить заново; закоммиченный в
  проекте или в личном слое (`~/.claude/`) — стоп, решение владельца (сессия его не удаляет),
  причина — в отчёт.
- Веб-интерфейс проверяется только с рецептом. Рецепт есть, если раздел профиля «Рецепт запуска для
  `/verify`» ссылается на файл `.claude/skills/run-<проект>/SKILL.md` и этот файл отслеживается git
  (`git ls-files --error-unmatch <путь>` — код 0); неотслеживаемый каталог `run-*` и другие скиллы
  `run-*` рецептом не считаются. Ветка меняет веб-интерфейс, а рецепта нет — стоп до запуска
  `scripts/canon/verify`: отчёт об остановке, причина — «нет рецепта: шаг „Рецепт
  `.claude/skills/run-<проект>/` — до пилота“ чек-листа переноса, `docs/transfer-checklist.md` в
  alexkabchina-arch/workflow». Рецепт заводит владелец при переносе встроенным
  `/run-skill-generator` (набранной командой дочернего `claude -p`; изнутри сессии он не виден), а не
  сессия тикета: генератор не запускать, драйвер руками не писать.
- Любое изменение `/verify` в `.claude/skills/run-*` — новый файл или каталог, правка или удаление
  отслеживаемого (после прогона — `git status --porcelain --untracked-files=all -- '.claude/skills/run-*'`
  не пуст) — стоп: итог проверки не засчитывается, изменения не коммитить, а откатить
  (отслеживаемое — `git checkout -- <путь>`, новое — удалить), что было изменено — в отчёт. Рецепт
  меняется только отдельным PR с ревью ошибок, как код.
- `.claude/skills/verify/` не коммитить, а удалить: проектный скилл с этим именем выключает
  встроенный `/verify`.

Проверка не подтвердила критерий тикета и исправить нельзя — не просить одобрить
непроверенное: отчёт об остановке.

## 5. Тело PR

Тело PR пишет скилл `pr` Мэтта — его разделы и правила, своего шаблона у `/ship` нет. Результат —
файл `/tmp/pr-<ветка>.md`. Доменный язык `pr` ищет в `GLOSSARY.md`; если в проекте его ещё нет, а
есть `CONTEXT.md` (не переименован при переносе), — в `CONTEXT.md`. Скилла `pr` нет в
`.claude/skills/` — стоп: канон поставлен не полностью (`canon-sync`), причина — в отчёт.

Факты канона — материал, который `pr` обязан включить, а не отдельный шаблон:

- `Closes #N`, если ветка закрывает тикет;
- в Evidence:
  - тесты и линтеры — какие команды, итог;
  - `/verify` — что проверено и итог, или строка «`/verify` не нужен: <причина>»;
  - ревью ошибок — найдено N: исправлено / отклонено (с причиной) / техдолг K (ссылка на тикет
    шага 2) / не записано M (вне диффа, не дефект) — числа сходятся с N; стоимость; пропущено —
    «только документы»; строка `review: предупреждение: …` — дословно. Списка находок вне диффа в
    теле нет: дефекты — в тикете, прочее не записывается;
  - перезапуск красного теста вне диффа (шаг 3), если был, — причина и что поправлено;
- в Merge Danger — что трудно откатить (миграции, изменение данных, внешние API) и пути-ограничители;
  PR на путь-ограничитель — строкой «проверка `restricted-paths` будет красной по замыслу: ждёт
  владельца, это не сбой CI».

## 6–8. Push, отметка ревью, авто-мёрж

Один вызов делает push, создаёт или обновляет PR, ставит отметку ревью (статус `review`) на
запушенный head и включает `gh pr merge --auto`:

```bash
scripts/canon/ship-finish --title "<заголовок>" --body-file /tmp/pr-<ветка>.md \
    --review-report /tmp/review-<ветка>.json [--ready-for-human "<строка из review или verify>"]
```

- `--review-report` — один отчёт полного ревью шага 1. Скрипт сверяет: начало диффа — в
  `origin/main`, head отчёта — HEAD или его предок; пропуск «только документы» перепроверяет по
  файлам до самого HEAD, ревью — по модели в отчёте. Иначе — отказ (код 2) с тем, чего не хватает:
  ветка переписана или отчёт чужой — ревью заново; код после пропуска «только документы» — ревью
  заново. Перерасход вдвое из отчёта скрипт помечает и сам, `--ready-for-human` для ревью можно не
  передавать.
- Коммиты после head отчёта — в описании отметки (head отчёта и их число) и списком в конце тела
  PR; самому их в тело не дописывать.
- Повторный `/ship` безопасен: второго PR не будет, отметка — только на итоговом коммите.
  Новый коммит после отметки её не наследует: отметку на него ставит только `ship-finish`.
- Повтор после того, как авто-мёрж уже слил PR (например, сессию доводят до `/ship` после обрыва) —
  «уже слит: <url>», код 0, ничего не делается. Тикет готов, в итог — ссылка на слитый PR.
- PR на путь-ограничитель (профиль, `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `scripts/canon/`,
  `.claude/settings*.json`, `.canon.lock`, `.github/`; точный список — `.github/CODEOWNERS`
  проекта) авто-мёрж не сольёт: обязательная проверка `restricted-paths` ждёт владельца. Это норма.
  Решать по самой проверке, не по списку: после `ship-finish` — `gh pr checks <PR>`; проверка
  `restricted-paths` красная или ждёт — отдельная фраза в итоге (ниже).

Код 1 или 2 — стоп, причина из stderr — в отчёт об остановке.

PR агент не сливает никогда и никаким способом: сливает GitHub авто-мёржем, который включает
`ship-finish`, или владелец. Ошибка самого `ship-finish` — обычный стоп по коду выхода (выше). Отказ
настроек на любую другую команду мёржа (`--admin`, `gh api` на мёрж) — правило, а не сбой: не
обходить, а сообщить в итоге.

## Итог

Одним сообщением: ссылка на PR; ревью (найдено / исправлено / отклонено / техдолг со ссылкой на
тикет / не записано, стоимость); тесты (перезапуск вне диффа — причина и что поправлено, если был)
и `/verify`; отметка на каком коммите и сколько коммитов после ревью; авто-мёрж включён. Проверка
`restricted-paths` на PR красная или ждёт — отдельной фразой «проверка `restricted-paths` красная
по замыслу: ждёт владельца, CI <итог>», где итог — job CI из профиля по `gh pr checks` в момент
итога: «зелёный», «идёт — проверить перед слиянием» или «красный». Остановка — ссылка на отчёт об
остановке (тикет или PR) и почему. Мёржа и CI не ждать.
