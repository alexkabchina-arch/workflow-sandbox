# /ship

Конец работы над тикетом ведёт скрипт канона `scripts/canon/ticket ship <N>` (N — номер тикета
из ветки `ticket-N`): ревью ошибок, разбор находок, тесты и линтеры профиля, `/verify`, догон
`origin/main`, тело PR, финиш через `ship-finish` (push, PR, отметка ревью, авто-мёрж). Механику
делает скрипт, суждение — агент по его заданиям.

## Цикл

1. Из корня worktree тикета, обычным Bash (не в фоне) с таймаутом 45 минут
   (`timeout: 2700000`); в описании команды — какой шаг идёт:

   ```bash
   scripts/canon/ticket ship <N>
   ```

   Ревью ошибок идёт 5–8 минут, `/verify` — до 7, тесты — сколько идут: вывода до конца шага
   нет, это не зависание.
2. Прочитать задание (блок `== … ==`) и выполнить его: ответ — в названный файл `.ticket/…`
   инструментом Write, правки кода — коммитами с сообщением одной строкой `-m`.
3. Вызвать скрипт снова той же командой — до последней строки `ticket: готово` или
   `ticket: остановка`.

Последняя строка вывода — статус. `ticket: ход агента` — задание твоё. `ticket: готово` — PR
открыт: привязать PR и включить Auto-fix, как сказано в выводе, затем `scripts/canon/ticket wait
<N>` (обычный Bash, таймаут 45 минут) — сессия ждёт мёржа сама и убирает за собой; его задания
(красный CI, конфликт) выполнять так же, до его «готово» («PR слит в ЧЧ:ММ») или «остановка»
(«ждёт: …»). Итог `ship` и итог ожидания — владельцу одним сообщением.
`ticket: остановка` у `ticket ship` — отчёт уже опубликован: передать владельцу причину; у
`ticket wait` — отчёта нет: передать владельцу строку «ждёт: …» из вывода.

## Правила

- Команды — как печатает скрипт (строки `▶`): без `cd`, `$(…)`, переменных, пайпов и
  многострочных аргументов — приложение отклоняет «слишком сложные».
- Шаг скрипта руками не подменять: ревью, тесты, `/verify`, PR и отметку делает только он.
  Ревью — одно на ветку: вызов после обрыва берёт готовый отчёт.
- Вопросы владельцу — только где их велит задание (вред тикета на другом пути, смысловой
  конфликт): до финиша, на языке поведения продукта.
- Довести нельзя — вопрос, варианты и рекомендация в `.ticket/stop.md`, затем вызов: отчёт об
  остановке собирает и публикует скрипт (комментарий, метка `ready-for-human`, PR — в черновик).
- PR агент не сливает никогда: `gh pr merge` не запускать ни с какими флагами. Сливает GitHub
  авто-мёржем или владелец; отказ настроек на команду мёржа — правило, а не сбой.
- Скрипт упал (код 1 или 2, причина строкой `ticket: …`) или классификатор auto mode отказал на
  его вызове — стоп: причину одной строкой владельцу, не обходить руками.

Как устроено — `docs/ticket.md` канона alexkabchina-arch/workflow.
