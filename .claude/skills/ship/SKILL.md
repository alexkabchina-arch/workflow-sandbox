# /ship

Конец работы над веткой. Сессия тикета мёржа **не ждёт**: включает авто-мёрж и завершается,
GitHub сливает PR сам после зелёного CI и отметки ревью. Проектные команды — из профиля проекта
`docs/agents/profile.md` (тесты, линтеры, ожидаемые job CI, критичные зоны, рецепт `/verify`).

Шаги строго по порядку. Красный шаг — стоп: исправить и пройти шаг заново или, если исправить
нельзя, — PR черновиком (шаг 7, `--unconfirmed`).

Тот же сбой второй раз без новой гипотезы — стоп и отчёт об остановке: что упало, что пробовал,
почему следующая попытка не поможет, варианты, рекомендация. Отчёт — шаг 7 с
`--unconfirmed "Отчёт об остановке: …"` (PR черновиком). Не проходит и он (push отклонён) — вручную
комментарий с первой строкой «Отчёт об остановке» и метка `ready-for-human`: есть PR — на PR,
предварительно `gh pr ready <PR> --undo`; PR нет — в тикете. Повтор без новой гипотезы только
тратит предел объёма сессии.

## 1. Ревью ошибок

Вся работа закоммичена. Из корня проекта, обычным Bash (не в фоне) с таймаутом 45 минут
(`timeout: 2700000`):

```bash
scripts/canon/review /tmp/review-<ветка>.json
```

- Код 0 и строка `review: пропущено` — дифф только из документов (`.claude/**` — скиллы, агенты,
  правила, а также `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` и профиль `docs/agents/profile.md` — не документы,
  ревьюятся). Отчёт о пропуске всё равно пишется в `/tmp/review-<ветка>.json`.
- Код 0 — находки списком в `/tmp/review-<ветка>.md`, их число — в строке `review: … находок: N`;
  «Находок нет» — законный итог. Строку `review: предупреждение: …` перенести в тело PR
  дословно; строку `review: ready-for-human: …` — передать на шаге 7 (`--ready-for-human`).
- Код 1 или 2 — ревью не состоялось (и когда список находок не распознан): стоп, причина из
  stderr — в отчёт пользователю. Без состоявшегося ревью отметку не ставить.

Отчёт `/tmp/review-<ветка>.json` — пропуск к отметке: `ship-finish` ставит её только по отчётам
ревью, которые цепочкой доходят ровно до запушенного head (шаг 7). Отчёт хранит, какой диапазон
проверен (`canon_review.base_sha`, `canon_review.head`).

**Полное ревью — один раз на ветку.** Второго полного прохода после исправлений нет.

**Прицельное повторное ревью.** Были коммиты после последнего отчёта (исправления по находкам,
правки по тестам, рецепт `/verify`) — одно на заход `/ship`, **после шагов 2–4, перед шагом 5**,
прицельное ревью только диффа этих коммитов, от head последнего отчёта:

```bash
scripts/canon/review /tmp/review-<ветка>-fix<k>.json --base <canon_review.head последнего отчёта>
```

`<k>` — номер захода: 1 — первый `/ship`, дальше — возвраты по красному CI (`session-start`
возвращает PR до двух раз), каждый — новый заход со своим прицельным ревью по диффу исправления.

Так же обычным Bash, не в фоне, с таймаутом 45 минут; строки `предупреждение` и `ready-for-human`
— как у полного. Коммиты только в документах — скрипт пропустит ревью бесплатно, но отчёт напишет.
Итог прицельного ревью — в тело PR отдельной строкой (найдено / исправлено / отклонено, стоимость).
Второго прицельного в том же заходе нет: находки прицельного в этой ветке не чинятся — «записано»
в тело PR или тикет; находка, без исправления которой PR сливать нельзя, — шаг 7 с `--unconfirmed`.

Повторный `/ship` после обрыва сессии берёт уже готовые отчёты ветки, если head в последнем из них
равен HEAD. Скрипт, запущенный снова с тем же отчётом, переносит его в `/tmp/review-<ветка>.prev.md`
(и `.prev.json`): упади новый прогон — оплаченные находки там.

## 2. Исправления

Ревью только находит, исправляет сессия. Каждую находку сверить с кодом и решить:

- **исправлено** — ошибка в строках, изменённых веткой: чинить в этой ветке, отдельным коммитом;
- **отклонено** — находка неверна: одна строка, почему;
- **записано** — находка о коде вне диффа: в этой ветке **не чинить**, записать в тело PR
  (или завести тикет и сослаться на него).

## 3. Тесты и линтеры

Полный сюит и все линтеры командами из раздела «Команды» профиля. Красное — исправить и
прогнать заново.

Долгие команды — через `run-log`, не через пайп: у `команда | tail` код выхода от `tail`, и
красный прогон читается как зелёный. Каждая команда профиля — отдельным вызовом из корня проекта,
обычным Bash (не в фоне) с таймаутом 45 минут (`timeout: 2700000`). Команда в профиле уже начинается
с `scripts/canon/run-log` — запускать как есть, второй раз не оборачивать; ещё не обёрнута —
обернуть:

```bash
scripts/canon/run-log -l tests -- <команда тестов из профиля>
```

Итог — код выхода вызова и последняя строка `run-log: завершено с кодом N`; на экране хвост,
полный вывод — в логе из той же строки. Ненулевой код — шаг красный, даже если хвост выглядит
зелёным. Длинный лог читать через `docs-scout`, не целиком в свой контекст.

## 4. `/verify`

По смыслу, а не по путям. Обязательна, когда ветка меняет наблюдаемое поведение (интерфейс,
ответ API, записываемые данные). Иначе — пропуск одной строкой в Evidence с причиной
(«`/verify` не нужен: …»), например «правка только документации».

Проверяет встроенный `/verify` — скриптом канона: он запускает дочерний `claude -p` с явным
диапазоном диффа, на закреплённой модели (проверяющий не слабее исполнителя), без меток сессии
тикета и сам проверяет, что проверка состоялась. `<ветка>` в путях ниже — имя ветки с `/`,
заменённым на `-`.

Критерии тикета — в файл `/tmp/verify-criteria-<ветка>.txt` (номер тикета и критерии приёмки,
как есть). Из корня проекта, обычным Bash (не в фоне) с таймаутом 45 минут (`timeout: 2700000`):

```bash
scripts/canon/verify /tmp/verify-<ветка>.json --criteria-file /tmp/verify-criteria-<ветка>.txt
```

- Код 0 и строка `verify: … PASS` или `… FAIL` — проверка состоялась: итог — поле схемы
  `verdict`, не текст; что проверено — в `/tmp/verify-<ветка>.md`, стоимость — в той же строке.
  В Evidence: что проверено (шаги, пробы мимо счастливого пути) и итог PASS / FAIL. Строку
  `verify: предупреждение: …` перенести в тело PR дословно; строку `verify: ready-for-human: …` —
  передать на шаге 7 (`--ready-for-human`), как у ревью; есть обе строки — одним аргументом через
  «; ».
- Код 0 и строка `verify: пропущено` — в диффе нет изменений (ветка без своих коммитов).
- Строка `verify: /verify оставил в рабочем дереве: …` (при коде 1 — в stderr) — разобрать каждый
  пункт: рецепт `.claude/skills/run-*` — см. ниже, `.claude/skills/verify/` — удалить, тестовые
  файлы — откатить; «коммиты /verify поверх ветки» — разобрать их файлы так же, лишнее откатить
  отдельным коммитом; «ветка сменилась» или «история ветки переписана» — стоп, ничего не
  откатывать, пункт — в отчёт.
- Код 1 или 2 — проверка не состоялась: стоп, причина и стоимость из stderr — в отчёт. `BLOCKED`
  (проверить не удалось: нет рецепта, нужен ответ человека) и «итог не распознан» — ответ
  `/verify` в `/tmp/verify-<ветка>.raw.md`, его суть — в отчёт. Отчёт прошлого состоявшегося
  прогона, если был, — в `/tmp/verify-<ветка>.prev.md`.
- Код 2 из-за своего `verify` (скилл `skills/verify/` или с `name: verify`, команда
  `commands/**/verify.md`): незакоммиченный в проекте — удалить и запустить заново; закоммиченный в
  проекте или в личном слое (`~/.claude/`) — стоп, решение владельца (сессия его не удаляет),
  причина — в отчёт.
- Веб-интерфейс проверяется только с рецептом `.claude/skills/run-<имя>/` (драйвер на Playwright,
  пишет встроенный `/run-skill-generator` тоже через `claude -p`). `/verify` может его создать или
  поправить: такую правку закоммитить — скилл ревьюится как код, поэтому после неё шаг 3, а
  перед шагом 5 — прицельное ревью шага 1 (оно покроет и рецепт).
- `.claude/skills/verify/` не коммитить, а удалить: проектный скилл с этим именем выключает
  встроенный `/verify`.

Проверка не подтвердила критерий тикета и исправить нельзя — не просить одобрить
непроверенное: шаг 7 с `--unconfirmed`.

## 5. Тело PR

Тело PR пишет скилл `pr` Мэтта — его разделы и правила, своего шаблона у `/ship` нет. Результат —
файл `/tmp/pr-<ветка>.md`. Доменный язык `pr` ищет в `GLOSSARY.md`; если в проекте его ещё нет, а
есть `CONTEXT.md` (не переименован при переносе), — в `CONTEXT.md`. Скилла `pr` нет в
`.claude/skills/` — стоп: канон поставлен не полностью (`canon-sync`), причина — в отчёт.

Факты канона — материал, который `pr` обязан включить, а не отдельный шаблон:

- `Closes #N`, если ветка закрывает тикет;
- в Evidence:
  - тесты и линтеры — какие команды, итог;
  - `/verify` — что проверено и итог, или строка «`/verify` не нужен: <причина>»;
  - ревью ошибок — найдено N: исправлено / отклонено (с причиной) / записано (вне диффа),
    стоимость; пропущено — «только документы»; строка `review: предупреждение: …` — дословно;
  - прицельное ревью, если было, — отдельной строкой: найдено, отклонено, записано, стоимость;
  - находки вне диффа — отдельным списком с пометкой «записано, не исправлено»;
- в Merge Danger — что трудно откатить (миграции, изменение данных, внешние API) и пути-ограничители.

## 6–8. Push, отметка ревью, авто-мёрж

Один вызов делает push, создаёт или обновляет PR, ставит отметку ревью (статус `review`) на
запушенный head и включает `gh pr merge --auto`:

```bash
scripts/canon/ship-finish --title "<заголовок>" --body-file /tmp/pr-<ветка>.md \
    --review-report /tmp/review-<ветка>.json [--review-report /tmp/review-<ветка>-fix.json] \
    [--ready-for-human "<строка из review или verify>"] [--unconfirmed "<причина>"]
```

- `--review-report` — все отчёты шага 1 ветки в порядке прогонов: полное ревью, затем прицельные
  прошлых и этого захода. Скрипт сверяет цепочку: первый отчёт — от `origin/main`, каждый
  следующий начинается с head предыдущего, последний — ровно HEAD, отчётов не больше четырёх
  (полное и по одному прицельному на заход); пропуск «только документы» перепроверяет по файлам,
  ревью — по модели в отчёте. Иначе — отказ (код 2) с тем, чего не хватает. Обычно это коммит
  после ревью: прицельного в этом заходе ещё не было — сделать его по шагу 1; уже было — второго
  нет, `ship-finish --unconfirmed` с причиной. Все отчёты — пропуск — отметка «только документы».
  Перерасход вдвое из отчётов скрипт помечает и сам, `--ready-for-human` для ревью можно не
  передавать. С `--unconfirmed` отчёт не нужен.
- `--unconfirmed` — критерий не подтверждён: PR черновиком без отметки, метка `ready-for-human`,
  комментарий с причиной. Причину писать так, чтобы владелец понял без сессии: вопрос, варианты,
  что сделано по умолчанию, рекомендация.
- Повторный `/ship` безопасен: второго PR не будет, отметка — только на итоговом коммите.
  Новый коммит после отметки её не наследует и без отчёта ревью по нему отметку не получит.
- Повтор после того, как авто-мёрж уже слил PR (например, сессию доводят до `/ship` после обрыва) —
  «уже слит: <url>», код 0, ничего не делается. Тикет готов, в итог — ссылка на слитый PR.
- PR на путь-ограничитель (профиль, `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `scripts/canon/`,
  `.claude/settings*.json`, `.canon.lock`, `.github/`) авто-мёрж не сольёт: обязательная проверка `restricted-paths` ждёт владельца. Это
  норма, сообщить в итоге.

Код 1 или 2 — стоп, причина из stderr — в отчёт.

PR агент не сливает никогда и никаким способом: сливает GitHub авто-мёржем, который включает
`ship-finish`, или владелец. Ошибка самого `ship-finish` — обычный стоп по коду выхода (выше). Отказ
настроек на любую другую команду мёржа (`--admin`, `gh api` на мёрж) — правило, а не сбой: не
обходить, а сообщить в итоге.

## Итог

Одним сообщением: ссылка на PR; ревью (найдено / исправлено / отклонено / записано, стоимость;
прицельное — отдельно);
тесты и `/verify`; отметка на каком коммите; авто-мёрж включён или PR черновиком и почему.
Мёржа не ждать.
