## Процесс — канон

Этот раздел ставит и обновляет установка воркфлоу (`canon-sync`); руками не править. Правила
проекта — вне него.

Процесс — канон `alexkabchina-arch/workflow`: скиллы `.claude/skills/` и `.agents/skills/`
(Codex), скрипты `scripts/canon/`, версия и список вендоренных файлов — `.canon.lock`.
Вендоренное руками не править: обновление — `canon-sync`, изменение процесса — PR в канон.
Проектная часть процесса — профиль `docs/agents/profile.md`; трекер и метки —
`docs/agents/issue-tracker.md`, `docs/agents/triage-labels.md`.

- **Процессом управляет владелец:** код пишется только после явной команды взять тикет в работу.
- **Тикет берётся одним входом — `/start N`:** скрипт `scripts/canon/ticket` ведёт подготовку,
  вопрос владельцу (`ticket ask`) и конец работы (`ticket ship`, `ticket wait`); его задания сессия
  выполняет без вопроса и подтверждения, красный шаг — стоп по его правилам. Код пишется по скиллу
  `/implement` Мэтта — по заданию `/start`, не отдельным входом.
- **Сессия на тикет:** `/start N` в сессии на главном чекауте сам зовёт
  `scripts/canon/session-start <N>`, затем переход в рабочую копию по пути из задания скрипта
  (EnterWorktree с `path`); из терминала — `scripts/canon/session-run <N>`, он тоже стартует с
  `/start N` (PR автора, взятый первым, — с заданием по PR). Главный чекаут всегда на `main`,
  разработки в нём нет. Как устроено — докстринг `scripts/canon/session-start` и
  <https://github.com/alexkabchina-arch/workflow/blob/main/docs/session.md>.
- **«Возьми тикет N» — координатор запускает исполнителя:** координатор — сессия, через которую
  владелец ведёт работу; код тикета он сам не пишет. По «возьми тикет N» он запускает исполнителя
  новой сессией рядом, с чатом (в Claude Desktop — соседняя сессия), со стартовым словом `/start N`
  (не `session-run` из Bash: там у `claude` нет терминала); в Codex — субагентом-исполнителем с
  заданием `$start N`, по одному за раз, и ждёт его результата. Не вышло запустить — второй раз не
  запускать (запуск мог пройти), а владельцу одна строка: где открыть сессию (главный чекаут
  проекта; Claude — Opus 5.5 medium) и что набрать (`/start N`, в Codex — `$start N`).
- **Вопрос исполнителя** (`ticket ask`) координатор видит в `/tickets`, по отчёту сессии или в
  результате субагента; в тикет пишет только ответ — по записанному со ссылкой на источник или
  «Ответ владельца: «…»» (замысел — владельцу в своём чате), затем «продолжай» в сессию
  исполнителя или продолжение того же субагента; их нет — новый `/start N`. Разведку, аварии и
  тикеты `ready-for-human` ведёт с владельцем; `/start` — после решений в тикете.
- **Исполнитель — всегда Opus 5.5 medium** (роль `session` таблицы `scripts/canon/v2/roles.py`,
  одной для всех ролей пути: ревью ошибок — xhigh, `/verify` — medium). Координатор запускает его
  с этими моделью и усилием явно, не наследством своей сессии; сам ниже Opus 5.5 medium (по данным
  приложения) — не запускает: сессию сильнее запускающей приложение не даёт, владельцу та же
  строка. После запуска сверяет модель и усилие исполнителя по данным приложения; расходятся —
  останавливает его с причиной владельцу. Сессия `/start N`, открытая руками, — тоже Opus 5.5 medium.
- **Codex — исключение из пункта выше:** модель, песочницу (маршруту нужны запись в `.git`, сеть,
  `claude` для ревью и `/verify`, хук по профилю) и подтверждения ставит владелец, сверки нет.
  Запреты Claude на Codex не действуют: в живом проекте исполнителя Codex нет, пока нет его защиты.
- **PR агент не сливает никогда и никаким способом; отказ на команду мёржа — правило, а не сбой.**
  Сливает GitHub авто-мёржем, который включает `ship-finish` на финише `/ship` (`scripts/canon/ticket ship`), или владелец;
  `gh pr merge` агент сам не запускает ни с какими флагами — даже на зелёном PR с отметкой.
  Отказ настроек на мёрж, отметку `review` (`gh api …/statuses`) и защиту `main` (`protection`,
  `rulesets`) — тоже правило: не обходить другим способом (curl, скрипт), а сообщить в итоге.
- **Конфликт слияния разрешает агент:** перед финишем `/ship` догоняет `origin/main` мёржем (не
  rebase) шагом «догон базы» `ticket ship`, с сохранением смысла обеих правок; свой PR в `CONFLICTING`/`DIRTY`
  `session-start` отдаёт следующей сессии первым — догон тем же шагом. Смысловой конфликт (две ветки
  по-разному меняют одну логику) — отчёт об остановке с вопросом владельцу.
- **Параллельно — только тикеты без общей миграции и без общего модуля ядра или экрана.** Общие
  документы и разные места одного файла — можно: такой конфликт сводит агент на догоне базы. Рекомендуя
  параллельную работу, назови у каждого тикета миграцию и модули или экраны, которые он правит.
- **Чужой тикет не трогать:** условие своего тикета не доделано — вопрос владельцу до финиша или
  новый тикет; в тикет, который делает другая сессия, ничего не дописывать.
